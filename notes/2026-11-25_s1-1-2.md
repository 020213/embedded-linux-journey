三个观察点
x/4xb p 报 Cannot access memory at address 0x1：0x1 不在进程合法地址空间，内核拒绝访问。这正是"这个指针不是分配来的"的直接证据。

病因：指针里装了一个从未合法过的地址，第一次解引用就踩空。
定位方法：gdb start → n 逐行 → 崩点 bt + info locals + p/x p + x/4xb p。
教训：野指针是三类里最好抓的，因为它必崩，而且崩点就是肇事行。
2 Bug 2 · 悬空指针
核心代码
c
char *msg = malloc(32);
if (!msg) { perror("malloc msg"); return 1; }
strcpy(msg, "T-Box: CAN frame received");
printf("[before] %s\n", msg);
free(msg);
/* msg = NULL;   ← 故意漏掉这行（S1-1-1 铁律③） */

printf("[after ] strlen = %zu\n", strlen(msg));   /* 悬空使用 */
printf("[after ] %s\n", msg);
裸跑：不崩
[before] T-Box: CAN frame received
[after ] strlen = ...
[after ] ...
$ echo $?
0
原因：malloc(32) < 128KB 走 brk 堆，free 只把块挂回 tcache，没有 munmap，页面仍然映射、仍然可读。读到的是元数据垃圾，但 CPU 不报错。

关键解读一：地址始终是 0x4052a0，一个字节都没动
free(msg) 后 msg 的值没变，变的是它指向的那 32 字节内容。gdb 引号里显示的是"解引用后的内容"，不是"指针的值"。

判断地址变没变：看 msg = 0x4052a0 这个十六进制数
判断内容变没变：看后面引号里的字符串
关键解读二："\005\004" 是 tcache 元数据，不是乱码
free 一块 < 512 字节的内存 → 进 tcache → 分配器把前 16 字节当 tcache_entry 用（前 8 字节 next，后 8 字节 key）。

glibc 2.32+ 的 safe-linking：e->next = (pos >> 12) ^ NULL，即

0x4052a0 >> 12  =  0x405
小端存储 0x405  =  05 04 00 00 00 00 00 00
                   ↑  ↑  ↑
                 0x05 0x04 0x00  ← 第三字节就是 0，所以 strlen 停在这
因此 strlen(msg) = 2，printf("%s") 打出的 0x05/0x04 是不可见控制字符，终端上看起来是空的。

验证命令：x/4xg msg（第一格 0x405，第二格非零 tcache key）。

三段闭环（valgrind 最大的价值）
Block was alloc'd at   →  main (1124_bug2_dangling.c:7)    ← 什么时候借的

第 7 行借，第 15 行还，第 19 行还在用。 gdb 拼不出这条线，因为它不记账。

为什么 gdb 里 strlen = 2，valgrind 里 strlen = 25
环境	strlen	原因
裸跑 / gdb	2	glibc tcache 接管，前 16 字节被元数据覆写，第 3 字节为 0
valgrind	25	valgrind 用自己的分配器替换 malloc/free，free 后不写链表元数据，只把 32 字节标成不可访问（红区），原数据原地保留
这才是悬空指针最凶险的地方：valgrind 下数据完好、输出完全正确，你以为程序没问题——但归属权已经交回去了，下一次 malloc 就能把它分给别人。

病因 / 定位方法 / 一句话教训
病因：free 之后指针没置 NULL，指向的内存归属已交回，但指针仍在使用。
定位方法：valgrind --leak-check=full，抓 Invalid read + free'd + 三段行号；gdb 只能证明"看不出异常"，不能证明没问题。
教训：地址值不变 ≠ 内存还是你的。free 之后立刻 p = NULL。

数字对账（三条独立线索互证）
① sizeof(struct frame) = 60，不是 64

成员：int  id            →  4 字节
      char payload[56]   → 56 字节
                    合计 = 60 字节

结构体对齐单位 = max(成员对齐数) = max(4, 1) = 4
60 % 4 == 0  →  尾部无需补齐  →  sizeof = 60
对齐只在不能整除时才补。若写成 payload[57] → 61 → 才补齐到 64。

② 泄漏块数 = 100

n % 3 == 0 在 0–299 中有 0, 3, …, 297，共 100 个。60 × 100 = 6,000 ✅

③ 19,024 的完整拆解

300 次 handle 里的 malloc × 60 字节   =  18,000
libc 首次 printf 的 stdout 缓冲区      =   1,024
                              合计   =  19,024  ✅ 与 total heap usage 一致
④ 301 / 201 这对数

项目	次数	组成
allocs	301	300 次自己 + 1 次 stdout 缓冲区
frees	201	200 次正常释放 + 1 次缓冲区
差值	100	正好是泄漏块数
⑤ valgrind 按"请求字节"记账，不按 chunk 实际占用

valgrind 报的 6,000  = 请求字节 60 × 100
真实堆占用           = chunk(60 + 8 → 补齐到 16 的倍数 = 80) × 100 = 8,000
hook 版（板子上没有 valgrind 时的唯一证据源）
c
static size_t g_alloc = 0, g_free = 0;

/* 必须先写函数本体，再下宏命令，否则 return malloc(sz) 会被自己替换成死循环 */
void *dbg_malloc(size_t sz, const char *file, int line)
{
    g_alloc++;
    (void)file; (void)line;
    return malloc(sz);          /* 此时替换还没发生，这里是真的 malloc */
}

void dbg_free(void *p)
{
    if (p) g_free++;
    free(p);
}

#define malloc(sz) dbg_malloc((sz), __FILE__, __LINE__)
#define free(p)    dbg_free(p)

void leak_report(void)
{
    fprintf(stderr, "[leak] alloc=%zu free=%zu diff=%zu\n",
            g_alloc, g_free, g_alloc - g_free);
}
预期输出：

[leak] alloc=300 free=200 diff=100
与 valgrind 差的那 1 次：hook 只统计你自己代码里的 malloc（300），valgrind 能看到整个进程（301）——多出来的 1 次是 libc 内部 printf 的 stdout 缓冲区。hook 看自己的代码，valgrind 看整个进程，两者互补，不能互替。

病因 / 定位方法 / 一句话教训
病因：n % 3 == 0 时提前 return，漏掉 free(n)，指针作用域结束后彻底丢失。
